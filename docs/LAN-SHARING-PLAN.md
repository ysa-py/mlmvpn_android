# پلن «شبکه محلی» — نسخه ۱.۲.۳

سند طراحی بخش تازهٔ «شبکه محلی» در نرم‌افزار اندروید MLMVPN.

**هدف:** کاربر بتواند اینترنت تونل‌شدهٔ گوشی را — با سیم یا بی‌سیم، از هر موتوری که روشن است — به دستگاه دیگری بدهد، بدون اینکه چیزی از پروکسی بداند.

**معیار موفقیت:** از لحظه‌ای که کاربر آیکون «شبکه محلی» را می‌زند تا لحظه‌ای که لپ‌تاپش آنلاین است، **هیچ عددی تایپ نشود**.

---

## ۱. سه محدودیتی که شکل کار را تعیین می‌کنند

هیچ‌کدام قابل دور زدن نیستند. هر طراحی‌ای که یکی از این‌ها را نادیده بگیرد یا کار نمی‌کند یا نشتی می‌سازد.

### ۱-۱. ترافیک دستگاه‌های تِتِرشده از VPN رد نمی‌شود

اندروید هات‌اسپات و تترینگ USB را با NAT در سطح کرنل انجام می‌دهد و upstream را از میان شبکه‌های «پیش‌فرض» انتخاب می‌کند. شبکهٔ یک `VpnService` هرگز کاندیدای upstream تترینگ نیست.

یعنی: **گوشی را هات‌اسپات کنید، VPN را روشن کنید، لپ‌تاپ وصل شود — لپ‌تاپ بدون VPN اینترنت می‌گیرد.** رفتار خود اندروید است، نه باگ ما.

> **نتیجه:** تنها راه واقعی اشتراک تونل، پروکسی محلی است. کل این بخش دربارهٔ آسان کردن همین یک کار است.

### ۱-۲. خود برنامه از تونل خودش بیرون است

هر دو سرویس همیشه `addDisallowedApplication(packageName)` می‌زنند تا حلقهٔ مسیریابی درست نشود — `TunnelVpnService.kt:3608` و `MyVpnService.kt:762`.

> **نتیجه:** یک «رلهٔ» عمومی داخل برنامه ممکن نیست — سوکت خروجی‌اش از تونل رد نمی‌شود و مستقیم و لو رفته بیرون می‌رود. اشتراک باید از لیسنر خودِ موتور بیاید.

### ۱-۳. هات‌اسپات را نمی‌شود مستقیم روشن کرد

`TetheringManager.startTethering()` مجوز `TETHER_PRIVILEGED` می‌خواهد که فقط اپ سیستمی دارد. تنها API در دسترس `WifiManager.startLocalOnlyHotspot()` است که عمداً اینترنت را به کلاینت نمی‌دهد.

> **نتیجه:** و همین برای ما کافی است — ما اینترنت را از upstream نمی‌دهیم، از پروکسی می‌دهیم.

### ۱-۴. قانون fail-closed

اگر تونل بیفتد، پروکسی باید **رد کند**، نه اینکه مستقیم بفرستد. Xray که بمیرد پورت بسته می‌شود و کلاینت `connection refused` می‌گیرد — یعنی رفتار امن از قبل درست است.

فایل PAC هم **هرگز** نباید `DIRECT` برگرداند. یک PAC که موقع قطعی به DIRECT برمی‌گردد، ترافیک کلاینت را دقیقاً در بدترین لحظه لخت بیرون می‌فرستد.

## ۲. ماتریس موتورها

| موتور | لیسنر فعلی | وضعیت | کار |
|---|---|---|---|
| خانوادهٔ Xray — V2Ray، اتصال سریع، کانفیگ رایگان، ابری، SNI | `mixed` روی `0.0.0.0:port` وقتی allow_lan روشن است (`XrayJsonGenerator.kt:37`) | ✅ کامل — TCP، UDP، احراز هویت، ACL | فقط UI |
| Psiphon | SOCKS + HTTP روی `any` (`TunnelVpnService.kt:1074`) | ✅ کار می‌کند | بدون رمز — هسته‌اش ندارد |
| Tor | SOCKS روی `127.0.0.1` | ⚠️ خاموش | تغییر bind به `0.0.0.0` |
| GST | لیسنر روی `127.0.0.1` | ⚠️ خاموش | همان |
| MASQUE / WireGuard / WARP-on-WARP | شاخهٔ `tun_fd` — هیچ لیسنری ندارند | ❌ در حالت VPN | **هر دو راه**، پایین |
| AmneziaWG / VPN Gate (SoftEther) | tun خالص، بدون شاخهٔ پروکسی | ❌ ممکن نیست | صادقانه گفته شود |

**برای موتورهای tun** — تصمیم کاربر، ۴ سپتامبر ۲۰۲۶: کارت وضعیت **هر دو راه را کنار هم** می‌گذارد.

1. دکمهٔ اصلی: **«روشن کردن حالت پروکسی»** — همین موتور را با شاخهٔ SOCKS بالا می‌آورد (`chainOuterJson` ثابت می‌کند که هسته این شاخه را دارد)
2. دکمهٔ فرعی: **«موتور دیگری انتخاب کنید»** — مستقیم به Xray یا Psiphon

هیچ‌کدام خودکار اتفاق نمی‌افتد. سوییچ خودکار یعنی یک قطعی ناگهانی تونل وسط کار کاربر.

**AmneziaWG و VPN Gate** همان کارت را می‌گیرند ولی فقط با دکمهٔ دوم، و یک جملهٔ صادقانه: «این موتور فقط tun است و پروکسی محلی ندارد».

## ۳. «شروع اشتراک‌گذاری» — یک دکمه، مثل بقیهٔ برنامه

اتصال سریع یک دکمه شد. پنل بازی یک دکمه شد. شبکه محلی هم یک دکمه می‌شود.

دکمهٔ بزرگ وسط صفحه این زنجیره را به ترتیب اجرا می‌کند و **در هر گامی که گیر کند، همان‌جا راه‌حلش را می‌دهد** — نه یک پیام خطا و نه هدایت به صفحه‌ای دیگر:

| گام | اگر مشکل داشت |
|---|---|
| ۱ — VPN روشن است؟ | دکمهٔ «اتصال» همان‌جا |
| ۲ — موتور فعلی لیسنر دارد؟ | دو دکمهٔ بخش ۲ |
| ۳ — `allow_lan` روشن است؟ | خودکار روشن می‌شود (کاربر همین را خواسته) |
| ۴ — آدرس محلی داریم؟ | دکمهٔ «روشن کردن هات‌اسپات» |
| ۵ — پورت واقعاً bind شده؟ | عیب‌یاب باز می‌شود |
| ۶ — وب‌سرور راه‌اندازی بالا آمد؟ | ورودی دستی به‌عنوان جایگزین |
| ۷ — QR و لینک آماده | ✓ |

چهار حالت دکمه با رنگ و حرکت خودشان، دقیقاً به زبان اتصال سریع: آماده (نفس می‌کشد) / در حال آماده‌سازی (کمان چرخان) / منتظر اولین دستگاه (نبض آرام) / در حال اشتراک (حلقهٔ سبز ثابت).

`NetworkSettings` تنها مالک تنظیمات می‌ماند — قانون موجود پروژه. کلیدهای تازه هم آنجا اضافه می‌شوند.

### ۴-۱. `LanShare`

```kotlin
data class LanStatus(
    val address: String?,        // از CoreConfig.localNetworkAddress
    val medium: Medium,          // HOTSPOT / USB / WIFI / ETHERNET / NONE
    val ssid: String?,           // فقط وقتی هات‌اسپات را خودمان ساخته‌ایم
    val engine: EngineShare,     // FULL / NO_AUTH / NEEDS_PROXY_MODE / IMPOSSIBLE
    val socksPort: Int, val httpPort: Int, val setupPort: Int,
    val vpnUp: Boolean,
    val clients: List<LanClient>,
    val seenSetupPageFrom: Set<String>,
)
```

`address` از `CoreConfig.localNetworkAddress()` — تابعی که سه بار در میدان اصلاح شده و قواعد `ap0`/`rndis0`/broadcast را می‌داند. **بازنویسی نمی‌شود.**

`medium` از نام اینترفیس درمی‌آید. همان رتبه‌بندی موجود داخل `localNetworkAddress` است که فقط باید بیرون داده شود.

## ۵. مسیر کلاینت — جایی که کار واقعاً آسان می‌شود

### ۵-۱. فایل PAC

ویندوز، مک، iOS و اندروید همگی فیلد «آدرس پیکربندی خودکار پروکسی» دارند. کاربر به‌جای تایپ IP و پورت و نوع پروکسی در سه فیلد جدا، **یک URL** می‌دهد.

چون محتوایش را ما تولید می‌کنیم:

- آدرس‌های LAN و لوکال مستثنا می‌شوند (`isInNet` → `DIRECT`) تا چاپگر و روتر و NAS از تونل رد نشوند
- برای Xray هم `PROXY` و هم `SOCKS5` روی همان پورت نوشته می‌شود (inbound از نوع `mixed` است)
- برای Psiphon پورت HTTP جدا می‌رود
- **هرگز `DIRECT` عمومی برنمی‌گرداند** — بخش ۱-۴

### ۵-۲. صفحهٔ راه‌اندازی که خودش سیستم‌عامل را می‌شناسد

`http://192.168.43.1:10811` — و صفحه از `User-Agent` می‌فهمد کلاینت ویندوز است یا مک یا آیفون، و **فقط راهنمای همان را نشان می‌دهد**. بقیه پشت یک لینک «سیستم‌عامل دیگر» می‌مانند.

روی صفحه:

- آدرس PAC با دکمهٔ کپی بزرگ
- برای ویندوز: **یک خط PowerShell آمادهٔ کپی** که همه‌چیز را ست می‌کند
- برای مک و لینوکس: خط ترمینال معادلش
- برای بقیه: مسیر منو با **نام دقیق گزینه‌ها به زبان خود آن سیستم‌عامل**
- نوار وضعیت زنده، بخش ۶

دوزبانه، و `dir="rtl"` وقتی زبان برنامه فارسی است.

> **چرا فایل دانلودی نمی‌دهیم:** یک فایل `.reg` برای ویندوز کار می‌کند، ولی آنتی‌ویروس‌ها فایل رجیستری دانلودشده را قرنطینه می‌کنند و این یعنی یک کوه تیکت پشتیبانی. یک خط PowerShell قابل کپی همان کار را می‌کند، چیزی دانلود نمی‌شود و کاربر می‌بیند چه دستوری اجرا می‌کند.
>
> **و چرا `.mobileconfig` برای iOS نمی‌سازیم:** پروفایل امضانشده صفحهٔ «Unverified Profile» نشان می‌دهد که ترسناک‌تر از خود کار است. مسیر دستی iOS پنج ضربه است. مسیر دستی برنده می‌شود.

### ۵-۳. سه نوع QR

| QR | محتوا | چه کار می‌کند |
|---|---|---|
| پیوستن به وای‌فای | `WIFI:S:<ssid>;T:WPA;P:<pass>;;` | دوربین اندروید و آیفون مستقیم به هات‌اسپات وصل می‌شود |
| صفحهٔ راه‌اندازی | `http://<ip>:10811` | مرورگر کلاینت باز می‌شود |
| PAC | `http://<ip>:10811/proxy.pac` | برای کلاینت‌هایی که فیلد PAC دارند |

QR اول فقط وقتی هست که هات‌اسپات را خودمان ساخته باشیم — چون فقط آن‌وقت رمز را می‌دانیم.

## ۶. حلقهٔ تأیید — «آیا واقعاً کار کرد؟»

مشکل بزرگ هر راهنمای پروکسی این است که کاربر مراحل را انجام می‌دهد و **نمی‌داند درست شد یا نه**. حل‌شدنی است، از دو طرف، با همان دادهٔ `/proc/net/tcp`:

**روی گوشی:** کارت وضعیت از «منتظر اولین دستگاه…» می‌رود به «۱۹۲.۱۶۸.۴۳.۵ وصل شد ✓» به‌محض دیدن اولین اتصال ESTABLISHED روی پورت پروکسی. با یک اعلان و لرزش کوتاه.

**روی خود کلاینت:** صفحهٔ راه‌اندازی هر دو ثانیه `/status` را می‌پرسد و گوشی جواب می‌دهد که آیا از IP همین درخواست‌کننده اتصال پروکسی می‌بیند یا نه. سه حالت:

- ⚪ «هنوز پروکسی را تنظیم نکرده‌اید»
- 🟢 «متصل — ترافیک شما از تونل رد می‌شود»
- 🟡 «پروکسی تنظیم شده ولی اتصالی نمی‌بینیم — احتمالاً پورت اشتباه است»

بدون CORS، بدون هیچ سرویس بیرونی، فقط دو طرف یک شبکهٔ محلی. کاربر لازم نیست چیزی را حدس بزند.

## ۷. عیب‌یاب

یک دکمه که ده چیز را روی گوشی چک می‌کند و هر کدام را با ✓ یا ✗ **و دکمهٔ رفعش** نشان می‌دهد:

| # | بررسی | منبع |
|---|---|---|
| ۱ | VPN روشن است | وضعیت سرویس |
| ۲ | موتور فعلی لیسنر دارد | ماتریس بخش ۲ |
| ۳ | `allow_lan` روشن است | `NetworkSettings` |
| ۴ | آدرس محلی داریم — و روی کدام اینترفیس | `localNetworkAddress` |
| ۵ | رسانه چیست: هات‌اسپات، USB، وای‌فای | `medium` |
| ۶ | پورت پروکسی واقعاً bind شده | تلاش اتصال به خودمان |
| ۷ | وب‌سرور راه‌اندازی بالاست | تلاش اتصال به خودمان |
| ۸ | آیا دستگاهی صفحهٔ راهنما را باز کرده | لاگ وب‌سرور |
| ۹ | آیا اتصال پروکسی می‌بینیم | `/proc/net/tcp` |
| ۱۰ | صرفه‌جویی باتری برنامه را نکشته | `isIgnoringBatteryOptimizations` |

گام ۸ مهم‌ترین است: اگر کلاینت صفحه را باز کرده ولی پروکسی وصل نشده، مشکل تنظیمات کلاینت است. اگر صفحه را هم باز نکرده، مشکل خود شبکه است — احتمالاً **جداسازی کلاینت‌ها روی وای‌فای عمومی**، که صفحه به‌صراحت اسمش را می‌برد و می‌گوید راه‌حلش هات‌اسپات خودِ گوشی است.

خروجی عیب‌یاب یک متن قابل کپی هم می‌دهد، برای وقتی که کاربر می‌خواهد از پشتیبانی بپرسد.

## ۸. امنیت

> **تصمیم کاربر، ۴ سپتامبر ۲۰۲۶:** رفتار پیش‌فرض دست نمی‌خورد. `DEFAULT_ALLOW_LAN = true` می‌ماند و رمز اجباری نمی‌شود. آنچه بهتر می‌شود، **هشدار** است.

### ۸-۱. هشدار زنده به‌جای پاراگراف متن

از همان `medium` که داریم:

- روی `ap0` یا `rndis0` → نوار سبز: «هات‌اسپات خودتان — فقط دستگاه‌هایی که خودتان وصل کرده‌اید»
- روی `wlan0` → نوار زرد: «روی وای‌فایی هستید که کنترلش دست شما نیست. هرکس روی این شبکه می‌تواند از تونل شما استفاده کند و مصرفش به حساب شما نوشته می‌شود» — با دو دکمهٔ کنارش: **«خاموش کن»** و **«رمز بگذار»**

دلیل این تصمیم: عوض کردن پیش‌فرض یعنی کاربری که امروز لپ‌تاپش از روی وای‌فای خانه وصل است، فردا بعد از آپدیت قطع می‌شود و نمی‌داند چرا.

### ۸-۲. چهار قابلیت اختیاری — همه پیش‌فرض خاموش

| قابلیت | چطور | محدودیت |
|---|---|---|
| **رمز پروکسی** | `accounts: [{user, pass}]` روی inbound از نوع `mixed` — هم SOCKS5 و هم HTTP را با یک تعریف پوشش می‌دهد. رمز ۶ رقمی خودکار، داخل PAC و QR | Psiphon ندارد؛ سوییچ خاکستری می‌شود با نوشتن دلیلش |
| **فهرست مجاز / مسدود** | قانون routing با `source` به `blackhole` | فقط خانوادهٔ Xray |
| **«فقط روی هات‌اسپات خودم»** | روی `wlan0` پروکسی روی loopback می‌ماند | — |
| **زمان‌سنج اشتراک** | ۳۰ دقیقه / ۱ ساعت / ۲ ساعت / بی‌نهایت، بعدش خودکار خاموش | — |

زمان‌سنج ساده‌ترین‌شان است و شاید پرکاربردترین: «توی کافه‌ام، نیم ساعت به دوستم بده».

### ۸-۳. مصرف شبکهٔ محلی

Xray یک stats API دارد که ترافیک را **به تفکیک inbound** می‌شمارد. در حالت VPN ترافیک خود گوشی از tun می‌رود نه از inbound، پس عدد inbound عملاً همان مصرف شبکهٔ محلی است.

نیاز دارد به `stats` و `policy.system.statsInboundUplink/Downlink` و یک inbound از نوع `api` در کانفیگ. کار دارد ولی شدنی است.

**پانویس صادقانه:** در حالت پروکسی، ترافیک خود گوشی هم روی همان inbound می‌نشیند و عدد مخلوط می‌شود. صفحه همان‌جا این را می‌نویسد به‌جای اینکه عدد اشتباه را قطعی نشان بدهد.

| **ویندوز ۱۰/۱۱** | Settings → Network & internet → Proxy → Use setup script → Edit | PAC، یا یک خط PowerShell |
| **مک** | System Settings → Network → Wi-Fi → Details → Proxies → Automatic proxy configuration | PAC |
| **آیفون / آیپد** | Settings → Wi-Fi → ⓘ → Configure Proxy → Automatic | PAC |
| **اندروید** | Settings → Network & internet → Wi-Fi → ⚙️ → Advanced → Proxy → Proxy Auto-Config | PAC |
| **اندروید تی‌وی** | Settings → Network & Internet → شبکه → Proxy settings → Manual | دستی: host + port |
| **پلی‌استیشن ۵** | Settings → Network → Set Up Internet Connection → Advanced → Proxy Server → Use | دستی: host + port |
| **لینوکس** | متغیرهای محیطی یا تنظیمات شبکهٔ گنوم | خط ترمینال |

تلویزیون و کنسول PAC ندارند و فقط host و port می‌گیرند — که برای inbound از نوع `mixed` روی همان پورت کار می‌کند، چون هم HTTP می‌فهمد هم SOCKS.

**تلویزیون‌هایی که اصلاً فیلد پروکسی ندارند** (سامسونگ Tizen، ال‌جی webOS) صادقانه گفته می‌شوند: از این گوشی نمی‌شود. راه‌حلشان سطح روتر است که از دست ما خارج است.

### چرا گام ۱۴ حذف شد

`libv2ray.CoreController` فقط سه متد آماری دارد و هر سه **outbound** هستند:
`queryStats(tag, direct)`، `queryAllOutboundTrafficStats()` و `measureDelay(url)`.
کلیدی که لازم داشتیم `inbound>>>socks>>>traffic>>>uplink` است و از این wrapper در دسترس نیست.

رسیدن به آن یعنی اضافه کردن یک inbound از نوع `api` به کانفیگ، یک قانون routing برایش، و یک
کلاینت gRPC داخل برنامه — کار زیادی برای عددی که در حالت پروکسی به‌هرحال با ترافیک خود گوشی
مخلوط می‌شد. و از سمت outbound هم جداشدنی نیست: ترافیک خود گوشی و ترافیک کلاینت‌ها روی همان
outbound می‌نشینند.

به‌جایش صفحه چیزی را نشان می‌دهد که **واقعاً می‌داند**: کدام دستگاه‌ها وصل‌اند و هرکدام چند
اتصال باز دارند. یک عدد درست کمتر، بهتر از یک عدد اشتباه بیشتر است.

## ۱۳. دوزبانگی

هر رشتهٔ تازه هم‌زمان در `values/strings.xml` و `values-fa/strings.xml`؛ هیچ literal فارسی داخل Kotlin. خواندن با `stringResource` در کامپوزبل‌ها و `S(R.string.x)` در بقیهٔ جاها.

سه نکتهٔ خاص این بخش:

- **صفحهٔ HTML وب‌سرور هم دوزبانه است.** زبان از `AppLocaleManager.isFarsi()` و `dir="rtl"` روی `<html>`.
- **اعداد همیشه لاتین می‌مانند** — IP، پورت، رمز — حتی در فارسی. یک IP با رقم فارسی قابل تایپ نیست. همان دسته باگی که قبلاً در `faDigits` پیدا و رفع شد.
- **نام گزینه‌های سیستم‌عامل ترجمه نمی‌شوند.** راهنما باید بنویسد `Use setup script`، نه ترجمه‌اش — کاربر دنبال همان کلمه روی صفحهٔ ویندوز می‌گردد. توضیح فارسی کنارش می‌آید، نه به‌جایش.
